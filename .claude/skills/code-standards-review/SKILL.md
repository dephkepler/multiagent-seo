# Нина Аркадьевна — Code Standards Review

Систематический проход по коду до прод-состояния.

Не путать с `/code-review` (ревью конкретного PR/диффа). Цель этого skill'а — довести кодовую базу
**в целом** до adequate prod state, по уже согласованному backlog'у, а не с нуля.

## Источник правды — не ищи проблемы заново
1. `doc/audit/audit-refresh-2026-08.md` — **начни отсюда**. Это ревизия `code-audit.md` от
   2026-08-16 (10 агентов проверили каждую находку по текущему коду): 68% старого аудита оказалось
   неактуально, здесь — реальный список живых пунктов по модулям. Бери оттуда, не из `code-audit.md`
   напрямую — номера строк там массово устарели.
2. `doc/audit/launch-readiness.md` — контекст запуска и приоритет 🔴 must-fix / 🟡 fast-follow /
   ⚪ defer (defer не трогать без отдельной просьбы); пункты 1-4 там уже закрыты.
3. `doc/audit/refactoring-backlog.md` / `doc/audit/constants-cleanup.md` — не ревизовались отдельным
   проходом (только `code-audit.md` проверяли) — при работе с ними сначала перепроверь актуальность
   находки по коду сам, как это уже делали для остального аудита, не доверяй строкам вслепую.
4. `doc/audit/code-audit.md` — только для полных формулировок/цитат кода, если краткой строки из
   audit-refresh не хватает для понимания. Сам по себе больше не источник приоритета.

Нашёл по пути проблему не из списка — не чини попутно (KISS: один пункт за раз). Допиши строкой в
подходящий `doc/audit/*.md` и вернись к текущему пункту.

## Правила
`.claude/rules/naming.md`, `error-handling-logging.md`, `solid-dry-kiss.md` — уже загружены через
корневой `CLAUDE.md`. Каждый фикс и весь новый код сверяй с ними. Полные версии с примерами —
`doc/standards/`.

## Цикл на каждый пункт
1. Возьми **один** самый приоритетный незакрытый пункт из списка выше.
2. Объясни, не чини молча: что не так, `file:line`, какое правило/находка нарушена, какой фикс
   предлагаешь. Коротко.
3. Жди явного "ок" на этот конкретный пункт — даже если предыдущий уже одобрили, новый пункт
   требует нового разрешения.
4. Правь. После правки — `cd backend && make lint && make test` (или `npm run lint` /
   `npm run typecheck` во frontend), если фикс в этой части дерева.
5. Отчитайся по файлам: путь → что делает → было/стало.
6. Отметь пункт закрытым прямо в исходном `doc/audit/*.md` (например ✅ рядом с заголовком пункта)
   — не удаляй формулировку, история должна остаться читаемой.
7. Не коммить и не пушь ни на одном шаге — это отдельное действие по явной просьбе.

## Стоп-условия
- Пункт трогает больше одного логического модуля/пакета — сначала предложи разбить на под-пункты,
  не хватай всё разом.
- Пункт противоречит контексту запуска из `launch-readiness.md` (единый аккаунт, англ-only,
  auto-publish выключен) — уточни у пользователя, не переоценивай приоритет сам.
