# SOLID / DRY / KISS — правила (дистиллят)

Полная версия с объяснением, «почему больно» и было→стало на нашем коде —
`doc/standards/solid-dry-kiss.md`. Приоритет при конфликте: **KISS/YAGNI > DRY** — простой повтор
дешевле неправильной абстракции.

## SOLID
- **S (Single Responsibility).** Функция > ~60 строк или > 1 «темы» → выдели под-шаги. Длинный
  метод = много состояния в голове = баг незаметен (так прятались два худших бага аудита в
  `pipeline()`).
- **O (Open/Closed).** Точка вариативности (LLM-провайдер и т.п.) → за интерфейсом + фабрикой, не
  `switch` с бизнес-логикой в сервисе.
- **L (Liskov).** Мок/альтернативная реализация обязана соблюдать тот же контракт, что настоящая —
  иначе тесты зелёные, прод падает.
- **I (Interface Segregation).** Несколько узких портов (`LLMClient`, `SERPProvider`,
  `ContentChecker`, ...) вместо одного толстого `Deps`. Порт объявлен там, где потребляется
  (`domain`), не рядом с реализацией в `infrastructure`.
- **D (Dependency Inversion).** Бизнес-логика зависит от интерфейсов, не от Postgres/Groq/WordPress
  напрямую; конкретика собирается в одном месте — `cmd/server/main.go`. > ~5 конструкторских
  аргументов → именованный `Deps`-struct, не позиционные параметры.

## DRY
Один и тот же паттерн ≥3 раз с реальной логикой внутри → выдели в хелпер (копия = фикс/баг
размножается во всех местах). Простой тривиальный повтор (`pickStr`/`pickInt`/`pickFloat`) —
оставь как есть: здесь DRY уступает KISS.

## KISS / YAGNI
Самое простое решение, которое работает. Не оборачивай, если нечего добавить (`List()` =
`return s.repo.List(ctx)`, лишний `fmt.Errorf` без новой информации — шум). Магические числа —
именуй (`estimateMaxTokens`, не `maxWords*3 + 200`). Не дроби функцию на микро-части ради метрики
строк — режь по смыслу, не по счётчику.

## Как этим пользоваться
Пишешь/ревьюишь код → прогоняешь по этим трём. Конфликтуют — выбирай простоту.
